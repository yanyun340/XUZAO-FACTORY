# ADR-0005 撤销用软作废 + 三条反向边，而不是删行或冲销

状态：已采纳｜日期：2026-11-26｜影响：R12、R12F、R16F、R25F｜代码：`backend/src/domain/flow.ts`、`domain/status.ts`、`routes/record-undo.ts`、`lib/clock.ts`

## 背景

任务书 R12 在 M 口径只要求「未支持的撤销明确拒绝，不允许随意删记录」，F 口径要求「到货、生产反馈、质检、包装、发货 10 分钟内安全撤销；超时管理员留痕修正」（验收 A17）。

本仓库此前只有明确拒绝：没有删除接口，状态机正向单向，「误操作」的答案是人工说明。补 R12F 时必须先回答三个问题：

1. 撤销是「删掉记录」还是「标记记录失效」；
2. 作废后订单状态怎么回到可继续操作的位置；
3. 谁在什么时间范围内有权撤销，超时怎么办。

A17 的预期已经给了约束：**「撤销是业务事件，不是删行」**，且要逐类核对累计、状态、时间线、通知。

## 决定

一、**软作废，不删行。**

- 五类记录（`arrival_records`、`production_feedbacks`、`qc_records`、`packing_records`、`shipment_records`）与 `qc_decisions` 增加 `voidedAt` / `voidedById` / `voidReason`；只有表达「谁在什么时候、为什么」的列，不改业务字段。
- 所有数量聚合（`computeQuantities`、`computeProfit`、看板 SQL）过滤作废行；订单详情仍返回作废行，供现场看到「这条被撤了、为什么」。
- 作废的质检决策视同「未决策」：既不放行、也不报废，也不再阻塞新一轮录入。

二、**状态只允许三条反向边。**

- `COMPLETED → SHIPPING`（发货量不足，同时清空 `completedAt`）；
- `QC_DONE → PENDING_QC`（不再结算）；
- `PENDING_QC → IN_PRODUCTION`（没有产量、没有质检、没有待复核异常）。
- 其余状态不因撤销而回退：`PACKING` 在包装量归零后仍是 `PACKING`，`SHIPPING` 在发货量归零后仍是 `SHIPPING`；这些情况下数量闸门会自己挡住后续动作。

三、**窗口与权限。**

- 10 分钟窗口内：记录的**原操作者**或**管理员**可以撤销；其他人 403。
- 超过窗口：只有管理员可以「修正」，必须填 2–200 字原因；事件与审计动作与普通撤销分开（`*_CORRECTED` / `*.correct`）。
- 下游依赖未解除一律拒绝，要求按依赖逆序撤销（A17 第 3、4 条）。

## 后果

- 记录不可删的既有口径不变；审计、时间线、数量复算都能解释每一次撤销。
- 撤销后可以继续正常录入（撤销到货后可重新登记、撤销反馈后可重新反馈、撤销质检后可重新检验、撤销发货后订单退回 `SHIPPING` 可重新登记），这条由 `undo.test.ts` 的「重做」用例锁住。
- 质检撤销必须连决策一起作废（同一事务），否则会留下「记录没了、放行量还在」的坏账。
- 已经进入包装或发货环节后，必须先按逆序撤销下游记录：否则会出现「状态卡在前一步、可执行动作为空」的死锁。守卫因此把「已下发包装」与「已触发发货」也算作下游依赖。
- 为测试窗口边界引入 `lib/clock.ts`（`now()` 可注入），窗口判断与 DTO 的 `canUndo` 共用同一时钟。

## 被否决的方案

- **物理删除记录**：直接违反 CONSTRAINTS「业务记录不可随意删除」，历史数量无法复算，审计也无法解释差异。
- **写一条负数冲销记录**：数量字段是 `Int` 且业务口径假设非负，冲销行会污染「记录条数」「最近一条」等语义，还要在每处聚合处理符号。
- **用通用状态投影从记录反推状态**：`PACKING` 与 `QC_DONE` 的区分依赖「是否下发过包装」这类事件事实，不在记录表里；强行投影会在没有包装记录时把订单打回 `QC_DONE`，反而造出新的死锁。只修三条明确的边更安全。
- **把下游依赖塞进 DTO 的 `canUndo`**：需要为每条记录多查一次下游表（N+1），而且与路由守卫重复；按钮可点、服务端给真实错误，与本仓库「隐藏按钮只是体验优化」的既有口径一致。
